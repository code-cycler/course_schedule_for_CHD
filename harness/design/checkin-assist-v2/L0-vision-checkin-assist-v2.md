## 目标与受众

**受众**：本人使用（长安大学学生；真机为荣耀 SER-AN00，Android 16 / SDK 36；畅课 `com.wisdomgarden.trpc` v2.16.0）。个人工具，无第三方用户，无合规审查义务，但边界与风险须书面留痕（见风险节）。

**目标 1 · 触达率**：把「教师发起签到 → 本 App 做出辅助动作（Mock 定位 + 提醒）」链路从「听天由命」升级为「每个已知断点各有自检、引导或兜底」。实测证据把断链点重定位到**本 App 侧**（进程被荣耀省电管控杀死、NLS 装机不重绑、电池白名单缺失），而非用户原始假设的「畅课不发通知」（畅课通知走荣耀厂商通道，进程死后大概率仍投递，见风险节假设 A）。

**目标 2 · 关联录入效率**：位置-课程-教室关联从自由文本升级为「课程下拉（仅当前学期）→ 自动预填该课全部教室 tag → tag 可增删改」，配合签到位置下拉选择，降低现场录入成本与错配率。

## 范围

### 做什么

1. **本 App 存活与 NLS 绑定加固**（W00 要点 1/2/7）：电池优化白名单申请与引导、荣耀「自启动」开关引导、`BOOT_COMPLETED` 开机拉活监听组件、NLS 绑定自检与 `requestRebind` 重连尝试；通知监听仍是主通道，在现有 `CheckInNotificationListener` 上加固而非推翻。
2. **触发源管线统一**（要点 8）：`CheckInTriggerCoordinator` 升级为「触发源（通知 / 轮询 / 手动 / 预留的自动签到）→ 签到会话级去重 → 响应动作」管线，多通道命中同一签到只响应一次（现 15 秒防抖升级）。
3. **轮询通道（带前置验证闸）**（要点 3/9）：主动轮询畅课 API 作为第二监听通道，仅覆盖「通知静默 / 被吞 / 文案不命中」场景；**验证闸 = 假设 B（签到 API 存在且可复用登录态）与假设 C（登录态来源）抓包/调研通过，闸门不过则该通道不做并记 OPEN-DECISIONS**；闸门通过前不写任何轮询代码。轮询仅课时有窗（当天有课的课前 N 分钟至课后 M 分钟，无课日不轮询；N/M/间隔定值归 L1）。
4. **位置编辑器重构**（要点 10–15 + 要点 11 补充声明补遗 + W01 Q2 裁决）：
   - 签到位置改下拉（从已有位置列表选择，「新建位置」入口保留，新建仍以现场采集 GPS 为主方式）；
   - 课程下拉数据源 = **仅当前学期**的本地课表课程名去重列表（补充声明裁决，推翻 W00 默认的「跨学期并集」），不联网拉课表，自由输入保留为 fallback；**历史学期已关联的位置保留原课程名原样显示与编辑，仅下拉候选限当前学期**；触发匹配按课程名照常全局生效——通知里的课程名与历史关联同名时自动命中，新学期同名课续用记忆（W01 Q2-D，零数据丢失、无额外 UI 状态）；
   - 选课程 → 自动预填该课**全部**教室为教室 tag（v120/v121 后一门课可挂多教室、分周换教室，全部带出，含线上教室名），预填可删可改，手输自定义教室仍允许；
   - `CheckInLocation.linkedRoomName` 单字符串 → `linkedRoomNames` 集合，Room v2→v3 迁移（旧单值 → 单元素集合），触发匹配升级为「任一教室 tag 命中即命中」；
   - 位置记忆 DataStore 键从「课程名|教室名 → 位置」升级为「课程名 → 位置」为主键，旧记忆迁移或废弃方案归 L1。
5. **手机端测试入口**（补充声明新需求 + W01 Q3 裁决）：签到窗口短、不一定能连电脑调试，以下四个入口为正式版能力，全部不依赖电脑——①**畅课通知原文记录器**（NLS 顺手记录最近 N 条畅课通知的渠道/标题/正文，本地存储 + 页面查看 + 可复制，假设 A 校准与关键字调试的主入口）；②**端到端通知自检按钮**（正式版内置「发送测试签到通知」，验证「通知 → 匹配 → 触发」全链路，现有 debug-only shell 钩子升级为正式入口）；③**NLS 绑定实时验证按钮**（点击发真实 ping 验证 `onNotificationPosted` 回调通不通，检测荣耀「授权了但没绑定」坑）；④**触发管线日志导出**（触发源/去重结果/选位置结果/Mock 状态写入可导出日志，复用现有日志导出链路）。另有条件项：**轮询手动触发按钮**随轮询通道闸门条件成立，不单独承诺。
6. **触发后提醒升级**（W01 Q4 裁决）：引导通知 channel 升级为 `IMPORTANCE_HIGH`（横幅 + 声音 + 振动），匹配签到短窗口（几十秒到几分钟）；自动拉起畅课维持现有开关、**默认关**（沿用 ADR-0001 决策 3，用户掌控）。

### 明确不做什么（边界硬约束）

1. **自动签到（调用畅课接口完成签到）本期不实现**（要点 4，单向门）：进范围仅指「触发源架构预留 + 未来用新 ADR 修订 ADR-0001」；实现闸门后置到「假设 B 抓包验证通过 + 用户显式二次确认 + 新 ADR 落盘」三条件齐备；即便未来实现也默认关闭、失败静默降级到现有「通知 + Mock」链路。ADR-0001「不调用畅课签到接口」条款**当前继续有效**。
2. **强校验签到永不自动完成**（要点 5）：二维码 / 手势 / 人脸 / 验证码类签到即便在自动签到方向成立后也一律排除，只提醒不代签。
3. **无障碍服务不进范围**（要点 6）：不引入 AccessibilityService。
4. **不做对抗系统的保活黑科技**（要点 7）：不做双进程互拉、1px Activity、常驻前台服务保命。
5. **签到辅助页非位置编辑器区块不动**（要点 10）：权限状态区、开关区布局保持现状（权限状态行的功能增强属第 1 项加固范围，不算布局重构）。

## 核心场景（W01 Q1 定稿：以下六场景全部为「必须支持」的验收场景）

- **S1 长期未启动后的第一签到**：手机重启或本 App 长期未打开，畅课签到通知经厂商通道到达 → 系统在 NLS 仍授权且未被解绑的前提下自动拉起监听组件 → 触发管线 → Mock 定位 + 引导通知。（技术事实：Android 的 NLS 绑定由系统管理，App 进程死亡本身不解除绑定；失效仅发生于通知使用权被关或荣耀装机/更新后不重绑。）这是「畅课和本软件都没启动」的原始痛点场景。
- **S2 NLS 解绑自检**：荣耀系统更新或本 App 装新包后 NLS 未被系统绑定 → 打开 App 自检发现 → 引导用户重开「通知使用权」（系统层行为，应用层只能引导）。
- **S3 关键字不命中兜底**：真实签到通知文案不含默认关键字 → 用户在设置页改关键字（现有能力）+ 畅课通知原文记录器辅助校准（范围第 5 项入口①）。
- **S4 畅课完全静默**：教师发起签到但服务器不推系统通知 → 轮询通道（若验证闸通过并实现）在课时有窗内发现 → 走同一触发管线。本场景按轮询闸门条件成立。
- **S5 现场快速选位置**：签到提醒已触发，用户点开 App → 位置下拉直接选，或按课程匹配 / 记忆自动选。
- **S6 多教室课命中当周教室**：一门课分周在不同教室（v121 场景）→ 触发时按当前周次实际教室匹配位置（教室 tag 任一命中即命中）。

## 验收标准（W01 Q5 定稿：A1–A9 全部为全链硬约束；条目可独立验证）

- **A1 真机可达性**：畅课进程强杀（最近任务划掉 + 强停）后发起真实签到，系统通知到达且本 App 触发完整链路（Mock 启动或引导通知）。此条同时裁决假设 A。
- **A2 通知文案校准**：记录真实签到通知的标题/正文实际文案，验证默认关键字「签到/考勤/点名」命中或已校准（吸收 TODO 遗留项「开学后校准签到关键字」）。
- **A3 单元回归**：`./gradlew test` 全绿，现有 134+ 用例零破坏。
- **A4 数据迁移**：Room v2→v3 迁移后，用户已存位置零丢失，`linkedRoomName` 旧单值正确变为单元素集合；触发匹配按「任一 tag 命中」工作。
- **A5 多源去重**：同一签到被多通道命中只响应一次（可用模拟触发 + 测试通知双源验证）。
- **A6 UI 验收**：位置下拉可选可新建；课程下拉仅列当前学期课程（历史关联原样保留显示）；选课后该课全部教室自动预填为 tag；tag 可增删改；手输教室仍允许。
- **A7 手机端自助测试**：范围第 5 项的四个入口（通知原文记录器 / 端到端测试通知按钮 / NLS 绑定实时验证 / 触发管线日志导出）全部不依赖电脑可用。
- **A8 行为回归**：现有通知监听、模拟触发、Mock 定位（启动/停止/超时恢复）行为不回退。
- **A9 提醒升级**：触发后的引导通知为 `IMPORTANCE_HIGH`（横幅 + 声音 + 振动）；自动拉起畅课开关默认关的行为不变。**验证三步**（grill W01 Q8 修订，防 MagicOS 通知智能分类降级）：① B3 真机装机后触发测试通知，用 adb `dumpsys notification | grep -A5 checkin_assist_alert_high` 或页内自检读取该 channel 实际 importance，确认未被系统降级；② 目视确认一次横幅弹出；③ 若被归类降级 → 引导用户在系统设置把该 channel 手动设为「紧急/横幅」，该引导做进 B4 警示条逻辑。

## 风险与约束

### 未验证假设台账（随波次更新）

| 假设 | 内容 | 状态 | 裁决方式 |
|---|---|---|---|
| A | 教师发起签到且畅课进程已死时，系统仍弹通知（厂商通道对签到类推送兜底） | pending（旁证：普通/营销推送走 `com.hihonor.android.pushagent`，`opPkg` 已实测） | 验收 A1 真机实测，手机端可自助 |
| B | 存在可复用登录态的畅课「进行中签到列表 / 提交签到」HTTP 接口 | pending（未抓包未调研；TronClass 社区有通用资料，CHD 部署未验证） | 抓包/调研，轮询与自动签到的共同前置闸 |
| C | 畅课登录态来源（复用学校 CAS 还是独立账号）与 Web 端域名 | pending | 随假设 B 一并验证 |
| D | `requestRebind()` 程序化重绑在荣耀 MagicOS 上有效（grill W01 Q1 揪出：v1 坑的处置是手动重开开关，程序化路径从未验证；javap 仅验证方法存在不验证行为） | **verified-无效（2026-10-14 真机裁决）**：冷启动调用返回 true 但未触发重绑（onListenerConnected 不出现）；`cmd notification allow_listener`（= 手动重开开关）有效 | **按设计降级纯引导**：警示条 +「去设置」已实现且装机场景实证有效（装机后警示条正确出现）；requestRebind 代码保留（无害，其他机型可能有效） |
| E | 开机 BOOT_COMPLETED 能到达 BootRebindReceiver | **verified-受控（2026-10-14 真机）**：荣耀 `HwMtmBroadcastResourceManager` BootProxy 以「don't meet cpuload」扣留广播（自启动管控），进程未拉起；receiver 注册与代码路径正确 | 用户在荣耀设置开启「自启动」白名单后预期生效；未开则依赖冷启动警示条引导路径（假设 D 降级后的兜底链） |

### 系统与合规约束

- **荣耀系统层坑**（DESIGN.md §7½ + retro）：NLS 装机不绑定需手动重开、后台保活受省电管控（本机实测未加电池白名单）——应用层只能引导与自检，无法自动修复。
- **学术诚信与协议风险**（ADR-0001 表述沿用 + 要点 18 升级）：虚拟定位与（未来的）自动签到可能违反畅课用户协议或学校考勤规定，风险由用户自行承担；若自动签到最终开工，须先落新 ADR 修订 ADR-0001 并明示学术诚信风险。
- **数据风险**：Room 迁移面对用户已存的真实标定数据，迁移脚本须有前置导出或可回退验证（细节归 L2）。
- **轮询若实现**：引入登录态维护成本与耗电，请求频率须克制（课时有窗已约束），避免对畅课服务器形成异常流量。

## 动机

用户原始痛点：「若畅课和本软件没有启动、没有后台，则监听不到消息；想要更健壮或多方式的监听，或伪造请求使签到成功；另外签到位置、关联教室应改下拉，选课程默认带出教室 tag，多教室考虑 tag 增删改。」

实测把第一诉求重定位：畅课通知走荣耀厂商通道（进程死后大概率仍投递），「畅课没启动」不是主断链点；主断链点在本 App 侧（被杀 + NLS 解绑 + 电池白名单缺失），故健壮性投资聚焦自身存活与绑定自检，轮询作为通知链路的兜底通道，自动签到作为带闸门的实验方向保留。UI 诉求（下拉与 tag）源于 v120/v121 揭示的多教室数据现实与现有自由文本录入的低效。
