# ADR 0004：签到位置用「采集当前真实 GPS」而非地图选点

**状态：** Accepted

## 背景

签到位置（用户上课地点）最初计划用地图 SDK 让用户在地图上点选。方案历经三次反转：高德 SDK（[ADR-0002](./0002-amap-map-sdk.md)）→ OSMDroid → 最终放弃「地图选点」范式本身。

反复换地图 SDK 的根因是「地图选点」这个范式自带四类成本，换哪家都躲不掉。

## 决策

**采集设备当前的真实 GPS 定位作为签到位置**，不再使用任何地图 SDK：
- 用系统 `LocationManager` 同时请求 `GPS_PROVIDER` + `NETWORK_PROVIDER`，谁先返回有效定位（`hasAccuracy()`）就用谁，10 秒超时。
- 坐标天然是 **WGS-84**，直接入库，无需任何坐标系转换。
- 室内 GPS 信号弱时，`NETWORK_PROVIDER`（Wi-Fi/基站定位）兜底——这正是百度等定位 SDK 室内定位的同源原理。
- 编辑页提供「采集当前位置」按钮 + 经纬度手动输入框（采集失败时 fallback）。

## 理由（一次性消除四类成本）

| 成本 | 地图选点（高德/OSMDroid/百度） | 采集真实 GPS |
|------|------------------------------|------------|
| Key 泄露 | 高德/百度需 Key 写 Manifest，可被反编译 | 不需要 Key |
| 坐标转换 | 高德 GCJ-02 / 百度 BD-09（双重）需转 WGS-84 | 原生 WGS-84，零转换 |
| 室内场景 | 地图点选要求用户知道教室位置 + 地图精度 | 站在教室里采即最准 |
| 依赖体积 | SDK + .so（高德/百度尤大） | 0（纯系统 API） |

签到位置的语义本就是「我上课的真实地点」——用真实 GPS 采集既最准，又把上面四类成本一并消除。

## 后果

### 正面
- 零 Key、零坐标转换、零地图依赖；`CoordinateConverter` 一并删除。
- 精度最高（采的是真实位置，而非地图上的估算点）。
- 室内有 `NETWORK_PROVIDER` 兜底，签到够用。

### 负面 / 已知限制
- 采集依赖用户**亲自到签到现场**点一次「采集」——首次录入位置必须人在现场。对「提前在家里录好所有教室位置」的场景不适用（但这种场景地图选点也不准）。
- 室内深处 GPS+网络都失败时，10s 超时后提示「到窗边重试」；用户可改用手动输入经纬度 fallback。
- 采集到的位置精度随环境波动（室内几十~几百米），保存时记录精度供用户参考。
