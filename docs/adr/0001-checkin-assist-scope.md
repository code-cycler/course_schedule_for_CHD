# ADR 0001：签到辅助功能范围与第一阶段边界

**状态：** Accepted

## 背景

用户希望在现有课表 App 中增加「签到辅助」功能：监听畅课（TronClass）的签到通知并开启虚拟定位。该需求的实现范围可以从「单纯提醒」到「全自动完成签到」之间大幅波动，不同边界对应的技术复杂度、权限需求、合规风险差异很大。

## 决策

1. **最终功能边界**：App 监听畅课签到通知 → 提醒用户 → 将系统虚拟定位临时切换到用户预先标定的位置；最终签到动作仍由用户在畅课 App 内手动完成。
   - **不做**：自动点击签到、破解/调用畅课签到接口、绕过验证码/手势/二维码/人脸识别等校验。
2. **第一阶段（初步实现）范围**：
   - 签到位置的增删改查（CRUD）。
   - 签到辅助设置页（权限状态、开关、Mock 时长、自动打开畅课开关等）。
   - Mock 定位前台服务 + 提醒通知 + 超时自动恢复真实定位。
   - 设置页内的「模拟触发」按钮，用于在没有真实畅课通知时验证端到端流程。
   - **暂不实现**：真实的 `NotificationListenerService` 监听 `com.wisdomgarden.trpc` 通知（见 [OPEN-DECISIONS.md](../OPEN-DECISIONS.md) 中的 deferred 条目）。
3. **自动打开畅课**：作为用户可开关的选项，**默认关闭**。

## 后果

### 正面
- 不触碰畅课内部协议，降低技术与合规风险。
- 实现复杂度可控，能在第一阶段跑通用户可感知的闭环。
- 用户始终掌控最终签到动作，避免误签、错签。

### 负面
- 「辅助」程度有限：用户仍需手动切换 App 并点击签到。
- 需要引导用户完成两个系统级设置：把本 App 设为「模拟位置信息应用」、开启通知使用权（第二阶段）。
- 虚拟定位本身可能违反畅课用户协议或学校考勤规定，需由用户自行承担风险；本 App 仅提供工具能力。

## 备选方案

| 方案 | 结果 |
|------|------|
| 半自动：自动打开畅课并跳转到签到页，用户只点确认 | 作为可选开关保留，默认不开启 |
| 全自动：解析通知后调用畅课接口完成签到 | **拒绝**，涉及协议破解与学术诚信风险，超出本阶段边界 |
