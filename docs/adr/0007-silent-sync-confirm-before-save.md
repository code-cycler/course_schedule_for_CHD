# ADR 0007：启动静默同步「先展示后确认」（检测到差异不自动入库）

**状态：** Accepted（2026-09-13，ux-perf-export L0 闸门用户裁决 + L1 契约确认）

## 背景

用户需求（W01）：「每次进软件静默同步，若有课程更新通知用户跳转，无或同步失败则无动作」。实现取向有两派：检测到差异后**自动入库再通知查看**（体验顺） vs **先展示差异、用户确认后才入库**（数据安全）。

## 决策

**先展示后确认**：启动/回前台（ON_RESUME，节流 15 分钟，独立开关默认开）→ 后台仅 OkHttp 拉取当前学期课表 → `ScheduleDiffCalculator` 纯函数 diff → 有差异弹 `AlertDialog` 差异清单（新增 N/删除 N/变更 N 门）→ **用户确认才走现有入库链路**（全量替换 + 冲突缓存重算）；取消/忽略则本地数据零变动。无更新、cookie 过期、网络异常一律完全静默。

## 理由

教务系统改版或解析异常可能产出「假更新」（错误课表数据）；静默场景用户没有防备，自动入库会用坏数据覆盖好数据且用户无感（L0-W01 已有先例：v120 多教室解析 bug 曾静默丢课程数据）。「先展示后确认」把最后一道门留给人，与用户原话「通知用户跳转」的动作语义一致（用户动作在前）。代价仅是确认多一次点击，且课程更新是低频事件。

## 后果

### 正面

- 假更新无法静默污染本地数据（最坏情况 = 用户看到可疑差异清单，选择不确认）。
- 用户对「我的课表被改了」始终有知情权与控制权。

### 负面 / 已知限制

- 多一次确认点击（接受：低频事件）。
- 「拉取不入库」需要从现有「拉取+入库」一体的 `fetchRemoteSchedule` 拆出只读变体（接口层小重构，契约见 L1）。
- cookie 失效时静默同步永远静默失败——用户需手动点同步才知道登录过期（符合「失败无动作」需求，但要有心理预期）。
